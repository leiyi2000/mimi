# 群撤回消息查询

> Yasuo 记录群撤回通知，并将当前群最近多条撤回消息渲染为图片。

## 1. 背景

Yasuo 已通过 `plugins/yasuo/tasks.py:NapCatSync` 归档群消息和图片。撤回能力进一步消费
NapCat SDK 的 `GroupRecallNoticeEvent`，其中包含原消息
`message_id`、原发送者 `user_id`、操作者 `operator_id`、`group_id` 和事件时间。

撤回通知本身不包含原消息正文，因此该能力必须把撤回事件与 Yasuo 已归档的
`GroupMessage` 关联。不能在收到撤回后再依赖 QQ 获取原文，也不能把未归档内容猜测或
描述为已找回。

## 2. 目标与非目标

### 2.1 目标

1. 持久化群撤回事件，容器重启后仍可查询。
2. 群成员发送 `群撤回 [数量]` 时，返回当前群最近多条撤回记录。
3. 每条记录展示用户头像、昵称、消息发送时间和消息内容。
4. 支持把已归档的撤回图片嵌入结果图。
5. 撤回事件存在但文本或图片没有存储时，保留该记录并明确标记缺失状态。
6. 明确区分本人撤回和管理员代撤回。
7. 对重复通知、原消息缺失和海报生成失败给出确定行为。
8. 允许按海报序号把已归档原消息作为 QQ 原生消息段单独发送。

### 2.2 首版不做

- 不支持私聊撤回。
- 不支持跨群查询、指定 QQ 号查询、无限翻页、历史导出或排行榜。
- 不提供撤回记录 HTTP API，避免扩大现有无鉴权 API 的数据访问面。
- 不恢复语音、视频、文件、合并转发或卡片中的外部资源。
- 不主动监听到撤回后立即公开原消息，只响应群成员命令。

## 3. 用户契约

新增群聊命令：

| 命令 | 权限 | 行为 |
| --- | --- | --- |
| `群撤回` | 当前群所有成员 | 查询当前群最近 5 条非机器人撤回消息 |
| `群撤回 <1-10>` | 当前群所有成员 | 查询指定数量的最近撤回消息 |
| `原始消息` | 当前群所有成员 | 单独发送最近一条撤回消息 |
| `原始消息 <序号>` | 当前群所有成员 | 单独发送从新到旧的第 N 条撤回消息 |

命令只接受纯文本和一个整数参数。私聊不响应；数量不是 `1-10`、包含多余参数、指定成员
或 QQ 号时返回对应命令用法，不隐式扩展查询范围。

成功时只发送一张纵向海报。海报中的每条记录包含：

```text
[头像] 张三                         发送于 10:20
       今晚开黑吗
       [已归档的撤回图片]
       撤回于 10:21
```

消息发送时间来自 `GroupMessage.time`，撤回时间来自 `GroupRecall.recalled_at`。当
`operator_id != user_id` 时，底部状态改为“由管理员撤回于 10:21”。首版不展示操作者
身份。

正文最长展示 1000 个字符，超出后明确标记“内容已截断”。消息只含不支持的类型时显示
可识别的类型占位，例如 `[语音]`、`[视频]` 或 `[文件]`，不显示原始 CQ 参数。

每条记录必须独立表达内容完整性：

| 归档情况 | 海报表现 |
| --- | --- |
| 撤回事件和原消息均存在 | 展示发送时间、文本和已归档图片 |
| 原消息整条未归档 | 展示头像和撤回时间；发送时间显示“未知”，内容显示“原消息未存储” |
| 原消息存在但无文本 | 不伪造空文本；若有图片则只展示图片 |
| 原消息声明含图但图片路径未保存 | 在对应图片位置显示“图片未存储”占位 |
| 图片路径存在但文件已丢失或不可读 | 在对应图片位置显示“图片不可用”占位 |
| 文本和图片均不可用 | 内容显示“消息内容未存储” |

缺失记录不能被过滤，也不能用更旧且内容完整的记录替代。请求 5 条且查到 5 个撤回事件
时，海报固定渲染 5 条记录，即使其中部分内容缺失。

失败提示保持明确：

| 场景 | 回复 |
| --- | --- |
| 当前群没有撤回记录 | `本群暂无撤回记录` |
| 数量参数非法 | 返回 `群撤回` 或 `原始消息` 的对应用法 |
| 数据库查询异常 | `查询撤回消息失败，请稍后重试` |
| 海报生成失败 | `生成撤回消息图片失败，请稍后重试` |
| 图片发送失败 | `发送撤回消息图片失败，请稍后重试` |

记录按撤回事件时间倒序，不设置隐含时间窗口。若未来需要保留期限，应作为独立的
数据治理设计处理，不能在查询层静默忽略旧记录。

`原始消息` 接受任意正整数序号，并通过数据库偏移直接定位单条记录，不批量加载前置历史。
文本和全部已归档图片作为一条 QQ 消息发送，不受
海报最多展示 4 张图片的限制。原消息、图片缺失或损坏时发送对应文字提示；语音、视频、
文件、卡片和合并转发因未归档其外部正文，只发送安全类型占位。消息末尾标注原发送者与
发送时间。

## 4. 数据设计

新增 Tortoise 模型 `GroupRecall`，表名为 `group_recalls`：

| 字段 | 类型 | 约束 | 含义 |
| --- | --- | --- | --- |
| `id` | `IntField` | 主键 | 内部记录 ID |
| `message_id` | `IntField` | 唯一、索引 | 被撤回消息 ID |
| `group_id` | `BigIntField` | 索引 | 事件所属群 |
| `user_id` | `BigIntField` | 索引 | 原消息发送者 |
| `operator_id` | `BigIntField` |  | 实际执行撤回的人 |
| `recalled_at` | `BigIntField` | 索引 | NapCat 撤回事件时间 |
| `created_at` | `DatetimeField` | 自动写入 | 本地首次落库时间 |

`message_id` 与 `GroupMessage.message_id` 采用逻辑关联，不建立数据库外键，原因是：

1. 插件可能在原消息到达后、撤回前重启，导致只收到撤回通知。
2. 历史数据库可能没有对应消息，但撤回事实仍应保留。
3. 撤回记录落库不能因原消息缺失而失败。

不删除或修改 `GroupMessage`。撤回是消息生命周期中的独立事实，原归档记录继续作为正文和
本地图片的唯一来源。新增表由现有 `Tortoise.generate_schemas()` 在空库和旧库中创建，
不要求修改已有 `group_messages` 表。新归档消息按图片段顺序保存路径；单张下载失败时在
`local_image_paths` 中保留 `null`，使后续海报能够定位具体缺失项。旧数据继续按已有路径
顺序兼容。

重复的 `GroupRecallNoticeEvent` 使用 `message_id` 幂等写入。若同一消息的重复事件字段
不一致，以首次记录为准并记录不含正文的警告，避免静默覆盖审计事实。

## 5. 处理流程

### 5.1 事件分发

`NapCatSync.start()` 仍是唯一 NapCat 消费入口，但事件处理拆成显式分发：

```text
NapCat event
  -> GroupMessageEvent
       -> MessageArchiveService.save()
       -> RecallCommandHandler.handle()
  -> GroupRecallNoticeEvent
       -> RecallService.record()
```

群消息先归档、后判断命令，确保查询命令本身仍遵守现有归档契约。撤回通知只写
`GroupRecall`，不在通知阶段主动发送消息。

单个事件处理失败只记录事件类型、群和消息 ID，不记录消息正文；随后继续消费下一事件。
只有 WebSocket 连接失败才触发现有五秒延迟重连，避免一条坏数据造成无意义断线重连。

### 5.2 查询

收到当前群的合法命令后，`RecallService.list_for_group()`：

1. 解析可选数量，默认 `5`，范围限制为 `1-10`。
2. 以命令事件的 `group_id` 查询 `GroupRecall`，先排除 `user_id == self_id` 的机器人
   消息，再按 `recalled_at` 倒序取指定数量。
3. 批量读取对应的 `GroupMessage`，关联条件同时包含 `message_id` 和 `group_id`。
4. 无对应 `GroupMessage` 的撤回事件仍转换为缺失状态的海报条目。
5. 将完整记录和缺失记录统一转换为 `RecallPosterItem`。

查询不能逐条访问数据库，避免数量增加后形成 N+1。先取得撤回事件列表，再用
`message_id__in` 一次读取对应消息，最后按撤回事件原顺序组装。

`group_id` 必须来自当前命令事件，命令参数不得覆盖它。这是同群访问边界，防止用户构造
其他群号查询。

### 5.3 海报领域模型

渲染模板不直接读取 ORM 实体。服务层输出普通 `dataclass`：

```text
RecallPoster
  -> generated_at
  -> items[]
       -> user_id
       -> display_name
       -> avatar_asset_key
       -> sent_at | None
       -> recalled_at
       -> recalled_by_admin
       -> text | None
       -> content_state
       -> images[]
            -> asset_key | None
            -> state
```

`content_state` 至少区分：

- `available`：正文或图片至少有一项可用。
- `message_not_stored`：只有撤回事件，没有 `GroupMessage`。
- `content_not_stored`：消息记录存在，但正文和图片均未保存。

图片 `state` 至少区分 `available`、`not_stored` 和 `unreadable`。模板只按这些状态绘制，
不得根据路径、空字符串或异常文本自行推断业务语义。

### 5.4 头像与昵称

昵称优先使用归档消息中的 `card`，其次使用 `nickname`。原消息没有归档时，
`GroupMemberResolver` 可通过 NapCat 的群成员信息接口补充昵称；查询失败时显示“群成员”，
但不影响整张海报。

头像由资产层根据 `user_id` 获取 QQ 头像，并在渲染前转为内存图片资产。头像请求设置显式
超时；失败时使用带用户昵称首字符的本地占位头像。模板不直接请求网络，也不持久化头像
URL 或 Base64。

同一用户在一张海报中出现多次时只获取一次头像。头像获取允许并发，但单个头像失败只
降级该用户，不得中止整张海报。

### 5.5 文本与撤回图片

`RecallContentParser` 读取 `GroupMessage.raw_message` 和
`local_image_paths`，输出文本摘要、消息中声明的图片数量及本地图片状态：

- 普通文字保留并进行 HTML 转义。
- CQ 消息段由解析器转换为安全摘要，不把 URL、文件路径或内部参数写入海报。
- 已保存且可读取的本地图片作为内存资产传给渲染器。
- 原消息声明了图片，但对应路径为空时生成“图片未存储”占位。
- 路径存在但文件丢失或读取失败时生成“图片不可用”占位。
- 语音、视频、文件、合并转发和未知消息段生成类型占位，不尝试恢复外部资源。

每条记录最多渲染 4 张图片缩略图，使用最多两列的自适应网格；超过 4 张时显示
“另有 N 张图片”，避免单条消息无限拉高海报。这里的限制只影响展示，不改变归档数据。

### 5.6 海报渲染与发送

Yasuo 按现有插件约定使用 Jinja2 生成 HTML，再由 `pytakumi` 渲染 PNG：

```text
RecallPoster + image assets
  -> templates/recall.html
  -> RecallPosterRenderer.render()
  -> PNG bytes
  -> base64://
  -> NapCat Image
```

海报采用固定 `1120px` 渲染宽度，高度随记录数量和消息内容增长。顶部只显示“群撤回消息”
和记录数量；主体是连续消息列表，不使用卡片嵌套。每条记录使用 `72px` 圆形头像，右侧
依次放昵称、发送时间、正文、图片网格和撤回时间。

渲染属于 CPU/浏览器阻塞操作，使用 `asyncio.to_thread()` 执行。远程头像和本地撤回图片
必须在渲染前加载为资产字典，HTML 中不保留外部网络依赖。最终 PNG 以 `base64://` 图片
消息发送，使 NapCat 无需访问 Mimi 容器内文件。

海报生成失败时只发送明确的文本错误，不静默退回不完整海报。发送失败不得删除撤回记录，
用户可以稍后重试。

## 7. 失败与一致性

- **重复群消息**：现有 `message_id` 唯一冲突应改为幂等读取，不得中断连接。
- **重复撤回通知**：保留首次记录，继续消费事件。
- **撤回先于可用归档**：撤回记录独立落库；海报保留条目并显示“原消息未存储”。
- **图片下载失败**：沿用现有局部成功策略，海报显示“图片未存储”占位。
- **图片文件丢失**：海报显示“图片不可用”占位，不删除整条记录。
- **头像获取失败**：使用本地占位头像，不中止海报。
- **部分记录组装失败**：该记录显示“消息内容不可用”，其余记录继续渲染。
- **海报渲染失败**：发送明确文本错误，不发送空白或半成品图片。
- **数据库失败**：记录结构化错误，不记录正文；命令侧返回统一中文错误。
- **WebSocket 断开**：等待五秒后重连，不无间隔重试。

SQLite 仍由单个 Yasuo 进程写入。查询与写入通过 ORM 独立语句完成，不引入跨进程锁或新
存储服务。

## 8. 隐私与滥用边界

撤回内容属于群内历史消息，首版采用以下限制：

1. 只能由群消息触发，且只能查询触发命令所在群。
2. 每次最多返回最近 10 条，不支持成员画像和批量历史导出。
3. 不增加 HTTP 撤回查询接口。
4. 日志只记录事件标识和错误类型，不记录正文、头像、图片 Base64 或本地路径。
5. 不恢复插件启动前未归档的消息，不把占位信息描述为原文。

如果后续要增加管理员专属历史查询、保留期限、成员退出后的数据处理或 HTTP 访问，必须
单独评审权限、认证和数据清理策略。

## 9. 验证计划

实现时至少覆盖：

1. `群撤回` 默认渲染 5 条，`群撤回 1` 和 `群撤回 10` 数量正确。
2. `0`、`11`、非整数和多余参数返回统一用法提示。
3. 每条记录包含头像、昵称、原消息发送时间和撤回时间。
4. 本人撤回和管理员代撤回的状态文案正确。
5. 文本加多图、纯图片、超过 4 张图片和超长文本布局正确。
6. 原消息整条未归档时仍保留撤回记录，并显示发送时间未知和“原消息未存储”。
7. 原消息存在但图片路径为空、图片文件丢失时分别显示正确占位。
8. 语音、视频、文件和未知 CQ 段只输出安全占位。
9. 两个群各自查询，只能命中本群记录。
10. 机器人自身撤回不进入群友查询结果。
11. 重复消息事件和重复撤回通知保持幂等。
12. 单事件数据库异常不触发 WebSocket 重连循环。
13. 头像下载失败使用本地占位头像，其他记录不受影响。
14. 旧数据库启动后自动新增 `group_recalls`，原消息查询不受影响。
15. 固定 fixture 渲染 `1`、`5`、`10` 条 PNG，验证非空、宽度、合理高度和无文字重叠；
    最终图片写入 `plugins/yasuo/tests/output/` 供人工检查。
16. `原始消息` 默认发送第 1 条，指定序号与海报顺序一致。
17. 单独发送覆盖文本、有效图片、未存储图片、损坏图片和整条原消息缺失。
18. `commands.toml`、Yasuo README、根 README 和帮助海报数据保持一致。

默认测试使用构造的 NapCat 事件和临时 SQLite，不连接真实 QQ 或外部图片服务。

## 10. 已确认设计

当前实现采用以下产品选择：

1. 海报命令名为 `群撤回`，原消息命令名为 `原始消息`。
2. 所有群成员可用，不限定群管理员。
3. 默认查询 5 条，允许指定 `1-10` 条，且不设时间窗口。
4. 结果始终以一张纵向 PNG 海报发送。
5. 海报展示头像、昵称、消息发送时间、文本、最多 4 张撤回图片和撤回时间。
6. 缺失正文或图片以记录内占位展示，不过滤该撤回事件。
7. 管理员代撤回只说明“由管理员撤回”，不展示操作者身份。
8. `原始消息 [序号]` 单独发送对应归档内容，序号不设上限，默认发送最近一条，并在末尾标注发送者与
   发送时间。
