# Niu 群级连续对话设计

## 1. 背景

改造前，Niu 只在消息以 `NIU_TRIGGER_PREFIX` 开头，或直接 `@` 机器人时进入对话。虽然
`ConversationStore` 保存了短期群聊上下文，但下一轮仍需重复写 `南瓜`。

连续对话不能按发起用户隔离。真实群聊中，其他成员会补充日志、纠正事实、发送图片或接着
追问；要求每个人重新唤醒，会把一个群话题错误拆成多段独立对话。

连续对话也不能依赖用户主动发送“结束对话”。多数对话自然停止于无人继续发言，退出命令
只能作为辅助能力，不能成为状态回收的主要机制。

本设计将连续对话建模为**群级短时话题窗口**：

- 任一成员显式唤醒 Niu 后，当前群进入活跃话题；
- 活跃期间，任何群成员都可以补充与当前话题相关的信息；
- 未显式唤醒的消息先经过相关性门控，避免 Niu 抢答无关群聊；
- 话题由空闲超时和最长存活时间自动关闭，不依赖用户手动结束。

### 1.1 实现状态

首轮实现已经落地群级 `topic_id`、双重超时、轻量相关性门控、`ignore/absorb/respond`
三态路由、其他插件命令排除、显式退出和上一话题检查点。相关陈述类补充使用 `absorb`
静默进入当前话题历史，后续问题可以读取；本轮没有增加定时批量聚合。

## 2. 目标

1. 显式唤醒一次后，当前群可以自然地多轮追问。
2. 群友无需重复前缀即可补充当前话题的关键信息。
3. 无关群聊不进入 Agent 上下文，不触发回复，也不延长话题寿命。
4. 对话自然停止后自动回到必须显式唤醒的状态。
5. 复用现有群 FIFO、多模态、引用消息、短期历史和安全边界。
6. 状态只保存在 Niu 进程内，不持久化完整群聊。

## 3. 非目标

- 不提供永久免前缀群聊模式。
- 不要求用户记住或主动使用结束命令。
- 不把每条活跃期群消息都无条件发送给 Agent。
- 不根据固定关键词判断自然语言是否相关。
- 不改变长期记忆、Yasuo 群历史或插件数据所有权。
- 不把多个群合并成同一个话题。

## 4. 用户契约

### 4.1 开启话题

任一成员发送以下消息，显式开启或切换当前群话题：

```text
南瓜 帮我看看这个报错
@机器人 帮我看看这个报错
```

消息必须通过现有校验并成功进入 `ConversationStore` 队列后才创建话题。空输入、超长输入、
重复消息、图片解析失败和队列已满都不会开启话题。

新的显式唤醒始终创建一个新话题世代，并把上一话题压缩为独立检查点传给新一轮。模型可以
承接相关信息，也可以在请求无关时忽略检查点。首轮仍维持每群一个活跃话题和一个 FIFO，
不并行运行多个群话题。

### 4.2 群友补充

话题活跃时，其他成员可以直接发送：

```text
这个错误只在生产环境出现
我补一张当时的截图
上面的版本号说错了，实际是 3.12
```

消息保留真实 `user_id` 和昵称，相关性门控及 Agent 都能区分信息来源。通过门控后，它与
显式触发消息走同一条处理链：

```text
QQ 事件
  -> 群级话题匹配
  -> 相关性门控
  -> QQMessageAdapter.parse()
  -> ConversationStore.accept()
  -> 当前群 FIFO
  -> AgentLoop
  -> QQ 回复
```

群友不是“接管发起人的会话”，而是参与当前群共享话题。管理员权限和用户身份仍取当前
消息发送者，不能继承发起人的权限。

### 4.3 显式插话与上一话题检查点

活跃话题中，任何群友再次使用 `南瓜` 或直接 `@机器人` 时，该消息是**强制插话**：

- 不经过普通相关性门控，保证明确请求不会被忽略；
- 不取消正在执行的 Agent Run；
- 不改变已经进入旧话题 FIFO 的消息归属；
- 在当前群 FIFO 中形成一个清晰的顺序边界。

插话消息成功入队后始终创建新的 `topic_id`，旧话题停止接收新消息。已入队的旧消息和正在
执行的 Agent Run 仍按 FIFO 完成。轮到新显式消息处理时，旧话题已经得到当时可获得的最终
结果，`ConversationStore` 将其压缩为 `PreviousTopicCheckpoint`，与新消息分区传给 Agent。

例如：

```text
A: 南瓜 帮我看这个 Python 报错
B: 南瓜 我补充一下，只在 3.12 出现
```

B 的消息拥有新 `topic_id`，同时收到 A 话题的检查点。模型可以把“只在 3.12 出现”作为对
上一问题的补充继续处理，不需要 B 重述完整背景。

```text
A: 南瓜 帮我看这个 Python 报错
B: 南瓜 查一下今晚的天气
```

B 同样收到上一话题检查点，但当前请求显然无关，模型忽略检查点并只处理天气。从 B 的显式
消息成功入队开始，后续普通消息只允许加入新 `topic_id`，不能落回旧话题。

检查点必须作为独立、低优先级结构传入，不能直接拼接到新用户原文：

```xml
<previous_topic_checkpoint>
  <goal>排查 Python 3.12 生产环境数据库连接超时</goal>
  <confirmed_facts>仅生产环境出现；使用连接池</confirmed_facts>
  <latest_result>初步排除 DNS，建议检查连接池耗尽</latest_result>
  <pending>等待完整错误截图和连接池配置</pending>
  <status>in_progress</status>
</previous_topic_checkpoint>
```

这样可以避免把历史中的群友文本伪装成当前用户指令，也让 Prompt 明确要求：

- 当前请求优先级高于上一话题检查点；
- 仅在语义相关时承接检查点；
- 不相关时不在最终答复中提及旧话题；
- 检查点是压缩背景，不是新的用户指令；
- 不根据检查点继承上一位成员的权限或身份。

检查点采用固定字段和字符上限，不递归包含更早的检查点。每个新话题最多接收紧邻的上一
话题检查点，避免多次显式唤醒形成无限摘要链。状态可取 `completed`、`in_progress`、
`partial` 或 `failed`，使新一轮能够区分已确认结论和未完成事项。

用户仍可用明确措辞帮助模型选择：

```text
南瓜 接着刚才的话题……
南瓜 换个话题……
```

显式插话先完成消息校验，再在成功入队时原子创建新 `topic_id`。普通消息在路由时记录观察
到的 `topic_id`，入队时执行比较并交换校验；若期间已有显式消息切换话题，则旧路由结果
失效并拒绝入队。相关性模型调用不持有群锁，不会阻塞显式消息。

### 4.4 自动结束

新增两个配置：

| 变量 | 默认值 | 范围 | 说明 |
| --- | --- | --- | --- |
| `NIU_CONTINUOUS_CHAT_IDLE_TTL` | `120` | `30..600` 秒 | 最后一个相关轮次后的空闲超时 |
| `NIU_CONTINUOUS_CHAT_MAX_TTL` | `900` | `120..3600` 秒 | 单个话题最长存活时间 |

话题满足任一条件即自动结束：

- 最后一个相关轮次超过空闲超时；
- 到达最长存活时间；
- Niu 进程关闭或重启；
- 新的显式唤醒成功入队并创建新话题。

只有通过相关性门控并成功入队的消息，以及对应 Agent 成功完成的回复，才刷新空闲截止时间。
Agent 回复仅在其 `topic_id` 仍是当前活跃话题时刷新。无关群聊、解析失败、队列拒绝、
模型错误和旧话题的延迟完成都不续期。最长存活时间永不刷新，防止活跃群聊让 Niu 长期处于
免前缀状态。

用户可以发送 `南瓜 结束对话` 提前关闭，但它只是可选捷径，不是正常使用流程的一部分。

## 5. 相关性门控

### 5.1 为什么必须门控

群级窗口若无条件接收所有消息，会产生三个问题：

- Niu 抢答群友之间的普通聊天；
- 无关消息污染当前 Agent 历史；
- 每条消息都触发完整 Agent Run，增加成本和延迟。

门控目标不是判断消息是否“有价值”，而是回答一个窄问题：

> 这条消息是否在继续当前 Niu 话题，因而应交给 Agent？

### 5.2 确定性高置信规则

以下消息不经过模型门控，直接进入当前话题：

- 包含 Niu 文本前缀；
- 直接 `@` 当前机器人；
- 活跃话题中的引用消息；

以下消息直接排除：

- 机器人自己发送的消息；
- 只 `@` 其他成员且没有引用当前话题消息；
- 命中其他插件完整命令；
- 当前群没有活跃话题；
- 当前话题已达到任一超时条件。

其他消息进入轻量相关性分类。

### 5.3 轻量分类

分类输入只包含：

- 当前话题的一句结构化摘要；
- 最近两轮已接纳消息的发送者和文本摘要；
- 候选消息的发送者、文本、表情描述、是否含图片；
- 是否紧跟 Niu 回复以及距上轮的时间。

分类输出为固定结构：

```json
{
  "action": "ignore | absorb | respond",
  "confidence": 0.0,
  "reason": "short machine-readable reason"
}
```

只有置信度达到 `0.7` 时才采用分类结果：`ignore` 不进入历史，`absorb` 静默写入当前话题，
`respond` 启动完整 Agent。分类器不调用 Tool，不生成用户可见文本，不读取长期记忆，也不
接收图片二进制。无法可靠判断的纯图片默认忽略并继续使用现有最近图片缓存。

门控失败时采用 `ignore`，同时记录错误码和指标。显式前缀、直接 `@` 和有效引用不依赖
分类器，因此分类服务异常不会导致用户明确请求静默失败。

### 5.4 无回复与补充信息

通过门控表示“属于当前话题”，不等于“每条都立即回复”。分类为 `absorb` 的事实补充直接
形成没有 assistant 文本的 `CompletedTurn`，不调用 Agent、不发送确认；下一个
`respond` 轮次按原发送者和顺序读取这些补充。该设计避免多个群友连续补充时逐条抢话，也
不需要定时窗口、空字符串暗号或额外批处理上下文。

## 6. 状态模型

连续对话状态归 `ConversationStore`，QQ 适配层只提供协议事实。

```text
IDLE
  | 显式消息成功入队
  v
ACTIVE
  | 相关消息成功入队 / Agent 成功回复
  |------------------------------------> 刷新 idle_expires_at
  |
  | 空闲超时 / 最长存活超时 / 显式关闭 / 进程关闭
  v
IDLE
```

实现状态：

```python
@dataclass(slots=True)
class ActiveTopic:
    topic_id: str
    opened_at: float
    idle_expires_at: float
    hard_expires_at: float
    summary: str
    accepted_message_ids: deque[str]
    previous_topic_id: str | None


@dataclass(frozen=True, slots=True)
class PreviousTopicCheckpoint:
    goal: str
    confirmed_facts: tuple[str, ...]
    latest_result: str
    pending: tuple[str, ...]
    status: str
```

状态键只有 `group_id`。成员身份记录在每条消息中，不把 `user_id` 放入话题键。

时间统一使用 `time.monotonic()`。`hard_expires_at` 创建后不可延长；过期项在每次消息匹配
时惰性清理。插件关闭时状态直接丢弃。

每条已接纳消息和待处理 Turn 都记录进入时的 `topic_id`。显式插话成功入队后，
`ConversationStore` 原子替换当前群的活跃 `topic_id`，并在新状态中记录
`previous_topic_id`。旧消息即使尚在队列中，也继续使用入队时绑定的旧上下文；新消息不得
根据处理时的全局状态重新归属，避免并发串线。

`CompletedTurn` 同样增加 `topic_id`。组装 Agent 消息时只选择当前 Turn 对应话题的历史；
旧话题可继续完成已入队工作。处理新话题的首条显式消息时，运行时从
`previous_topic_id` 对应的已完成轮次生成一次性检查点；新话题不会直接读取旧话题原始
轮次。后续同话题消息从同一组最多四个旧轮次确定性重建相同有界结构，不调用额外模型。

旧 Run 完成时仍写入其自身 `topic_id` 的历史和检查点来源，但只有
`completed_topic_id == active_topic.topic_id` 才能刷新当前话题超时或摘要。该比较必须在
状态提交处执行，不能依赖“通常按 FIFO 完成”的时序假设。

### 6.1 话题摘要

相关性门控不能直接消费全部 Agent 历史。每次 Agent 成功完成后生成或更新一句受限长度的
话题摘要，例如：

```text
正在排查 Python 3.12 生产环境中的数据库连接超时，等待错误截图和连接池配置。
```

摘要由已接纳的用户文本和成功 Agent 回复有界合并到最后 1000 字符，只服务于当前进程内
门控，不写入长期记忆；分类同时最多使用最近两轮当前话题历史。

### 6.2 上一话题压缩

检查点从上一 `topic_id` 最后四个 `CompletedTurn` 确定性组装：首条用户消息作为目标，
后续用户消息作为已确认事实，最近一次 assistant 文本作为最新结果，最后 Run 状态决定
`completed`、`partially_completed`、`failed` 或 `in_progress`。字段分别限制长度，不调用
额外模型、不读取长期记忆，也不递归包含更早检查点。

## 7. 回复归属

群友加入后，默认回复发送到群，不自动 `@` 最初发起人。需要明确提醒某位成员时，Agent
继续使用现有 `mention_current_sender`，其目标是触发本轮处理的当前发送者。

静默吸收的每条消息仍保存独立发送者。触发 `respond` 的当前消息继续作为
`ToolContext.current_sender`；历史补充只提供事实来源，不继承当前发送者权限。默认回复
不 @，需要提醒当前触发者时继续使用现有 `mention_current_sender`。

## 8. 与现有历史的关系

群级话题与当前 `ConversationStore` 按群维护 `CompletedTurn` 的结构一致。连续对话只改变
“普通消息是否进入 Niu”，不扩大持久化范围。

边界如下：

- 相关性门控拒绝的消息不写入 Niu 短期历史；
- 接纳消息继续保留发送者 ID 和昵称；
- 话题结束不删除现有短期历史，历史仍按 `NIU_HISTORY_IDLE_TTL` 独立过期；
- 退出话题不删除长期记忆；
- 完整群聊查询仍只能通过 Yasuo 的只读接口按需执行。

## 10. 失败行为

| 场景 | 行为 |
| --- | --- |
| 显式消息校验失败 | 返回现有错误，不开启话题 |
| 相关性分类失败 | 普通候选消息忽略并记录错误；显式消息不受影响 |
| 无关群聊持续发生 | 不接纳、不刷新，话题按原截止时间结束 |
| Agent 调用失败 | 返回现有错误，不因失败结果刷新话题 |
| Niu 进程重启 | 所有话题回到 `IDLE` |
| 多个群友连续补充 | 保留发送者和顺序，按 `absorb` 静默进入历史 |
| 群友再次显式唤醒 | 创建新 `topic_id`，附带上一话题检查点 |
| 上一话题仍在执行 | 不取消旧 Run；新话题按 FIFO 等待其完成后取得检查点 |
| 上一话题没有可用轮次 | 不注入检查点，新的显式请求照常执行 |
| 用户执行其他插件命令 | 只交给目标插件，不进入话题 |
| 纯图片无法判断相关性 | 保留最近图片缓存，不自动触发 |
| 达到最长存活时间 | 结束话题；下一条普通消息不触发 |

## 11. 测试矩阵

### 11.1 群级话题

- 任一成员显式触发后创建群级话题。
- 其他成员的相关补充可被接纳。
- 同一成员在其他群不能复用话题。
- 无关消息不进入历史，也不刷新空闲时间。
- 空闲 TTL 和最长 TTL 独立生效。
- 最长 TTL 不因持续相关消息延长。
- 进程关闭后不保存话题状态。
- 每次显式插话都创建新 `topic_id` 并记录 `previous_topic_id`。
- 话题切换不取消正在执行的旧 Run。
- 旧 Run 延迟完成不刷新新话题的超时或摘要。
- 切换后的普通消息不会进入旧话题。
- 插话校验或入队失败时不提交话题切换。
- 同群普通消息在入队时通过 `topic_id` 比较拒绝过期路由结果。
- 新话题只接收有界检查点，不直接加载旧话题原始轮次。

### 11.2 相关性门控

- 前缀、直接 `@` 和有效引用绕过分类。
- 只 `@` 他人的消息直接排除。
- 其他插件命令直接排除。
- 高置信相关补充接纳，低置信或无关内容忽略。
- 分类超时、非法 JSON 和 Provider 错误默认忽略。
- 分类错误不影响后续显式触发。
- 门控输入不包含图片 Base64、长期记忆或无关历史。

### 11.3 上一话题检查点

- 检查点包含目标、已确认事实、最新结果、未完成项和状态。
- 当前显式请求与上一话题相关时，Agent 可以正确承接。
- 当前显式请求无关时，Agent 不在答复中提及上一话题。
- 检查点与当前用户消息使用独立 section，不做字符串拼接。
- 检查点不继承上一成员身份、管理员权限或 Tool 授权。
- 检查点不递归包含更早检查点。
- 上一话题没有完成轮次时不注入检查点，新的显式请求仍正常执行。

### 11.4 多成员与静默吸收

- `absorb` 消息不调用 Agent，也不发送确认。
- 后续 `respond` 可以读取同话题内已吸收消息及其发送者。
- `absorb` 不继承发送者权限，当前 ToolContext 仍属于触发 `respond` 的成员。
- 当前群 FIFO 和消息顺序保持不变。

### 11.5 配置与文档

- 默认空闲 TTL 为 120 秒，最长 TTL 为 900 秒。
- 最长 TTL 必须大于等于空闲 TTL。
- 非整数和越界配置在启动时明确失败。
- `commands.toml`、插件 README、根 README 和部署规范保持一致。
