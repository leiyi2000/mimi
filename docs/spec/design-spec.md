# 设计规范

本文件定义 Mimi 的设计期规则。当前系统形态见
[`ARCHITECTURE.md`](../../ARCHITECTURE.md)，实现期硬约束见
[`AGENTS.md`](../../AGENTS.md)。

## 1. 插件边界

- 一个业务域对应一个 `plugins/<name>/`，拥有独立入口、依赖、测试和数据。
- 插件之间不直接 import；需要共享时先定义稳定协议，再决定是否抽取公共能力。
- 根 `mimi/` 只拥有插件发现、进程生命周期和基础 NapCat 连接。
- 原生或异构运行时通过窄 HTTP 服务隔离，QIMEI 是当前实例。

## 2. 代码分层

依赖方向保持：

```text
entry/config -> dispatcher -> feature -> service/model -> rendering
```

- 命令处理器负责参数、权限、编排和用户反馈。
- 外部响应在服务边界转换为 `dataclass`，模板不解析原始 JSON。
- Tortoise 模型只表达持久化，不承载 HTTP 或消息发送。
- 海报构造器只生成模板上下文和资产列表，图片获取由资产层处理。

## 3. 状态设计

- 登录态必须有唯一所有者，不能由多个服务各自保存副本。
- LOL 和网易云采用管理员维护的共享账号；普通用户绑定只保存查询偏好。
- 缓存必须可判定失效。QIMEI36 以设备 profile digest 校验。
- SQLite 只由所属插件进程写入。出现多副本写需求时，先重新评估存储。

## 4. 外部接口

- 使用 `httpx` 和显式超时。
- 认证、User-Agent、错误归一化放在客户端边界。
- 独立请求可以并发；允许降级时保留局部成功结果。
- 不根据不稳定表现猜测业务语义。例如掌盟错误不能统一解释为隐藏战绩。
- 上游没有提供的数据不得伪造。

## 5. 设计评审触发条件

以下变化先更新设计，再实施：

- 新增顶级运行服务或改变插件进程模型。
- 改变状态所有权或数据卷路径。
- 引入跨插件代码依赖。
- 替换 ORM、渲染引擎、消息协议或主要外部服务。
- 打破根 `AGENTS.md` 的任何架构不变量。
