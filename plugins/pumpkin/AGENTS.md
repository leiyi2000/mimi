# Pumpkin 插件开发指南

本文件约束 `plugins/pumpkin/`。Pumpkin 是面向 QQ 群聊和私聊的 AI 虚拟人物，
以自然对话为主要能力，任务执行为辅助能力。实现位于 `adapters/`、`core/`、
`persistence/`、`runtime/` 和 `providers/`，本文中的会话、人格和模型能力是已落地
实现必须遵守的边界。

## 1. 插件边界

- 所有 Pumpkin 业务代码留在 `plugins/pumpkin/`，根目录只负责插件发现、进程编排和
  基础 NapCat 连接。
- 不直接导入其他插件的实现。需要群消息归档、媒体处理或其他能力时，使用明确的公共
  契约或外部接口。
- 对话上下文、人格配置、用户偏好和运行数据由 Pumpkin 自己负责；运行数据放在插件
  的 `data/` 目录并持久化挂载，不进入 Git 或 Docker 构建上下文。
- Pumpkin 的核心输出是对话回复。任务执行、Artifact 登记和文件发送均通过显式工具、
  作用域校验和任务 revision 约束，不能破坏对话上下文和回复链路。

## 2. 对话优先

- 每条进入 Pumpkin 的消息都经过统一的消息适配和对话路由，再决定回复、追问、转交
  能力或保持安静。
- 群聊需要考虑消息是否真正指向 Pumpkin，避免抢答、重复回复和机器人自触发。
- 会话状态、上下文窗口、并发和取消必须由显式对象或服务管理，不能依靠模块级全局
  变量或隐式上下文。
- 回复生成与消息发送解耦。模型输出先转换为结构化结果，再由渠道层处理文本、图片、
  文件和失败反馈。
- 正常业务回复由模型根据当前上下文生成。仅网络不可用、模型不可用、权限失败等基础
 设施错误允许使用简短且明确的降级提示。

## 3. 禁止硬编码解决行为问题

这是本插件的核心规范：

- 不通过新增关键词判断、分支堆叠、特例列表或固定回复，修补某一条对话样本。
- 不通过不断追加提示词，把具体用户案例、历史错误答案或临时规则硬塞进人格提示词。
- 不在代码和提示词中复制同一套业务规则，避免两套规则逐渐不一致。
- 不轻易新增配置项。新增配置前必须证明现有配置、稳定常量或运行时数据无法表达需求，
  并说明它的部署差异、变更频率、默认值和兼容行为；只影响单个样例的参数不进入配置。
- 助手名称必须通过配置或依赖注入提供。代码、提示词、测试 fixture、日志文案和用户可见
  回复中都禁止硬编码某个具体助手名称；名称变化不能要求修改业务逻辑或提示词模板。
- 发现模型行为不符合预期时，先确认问题属于消息结构、状态管理、工具契约、模型配置、
  评测数据还是提示词设计，再修改对应责任层。
- 稳定的人格、边界和输出协议可以写入版本化配置或主提示词；具体行为应由结构化上下文、
  工具结果、会话状态和可验证的评测用例驱动。
- 需要新增例外时，先判断它是否是通用协议。如果只是为了通过单个样例，不应加入生产
  代码或提示词。

允许硬编码的内容仅限于确定性的基础设施约束，例如超时、重试次数、权限校验、消息
格式解析、状态迁移和外部协议字段。它们不能替代模型对语义、意图或人格的判断。

## 4. 推荐分层

新增功能按以下依赖方向组织，避免把所有逻辑堆到 `main.py`：

```text
NapCat message
    -> adapter / ingress
    -> conversation router
    -> session and context service
    -> model provider / tool use
    -> structured reply
    -> channel renderer / sender
```

- `main.py` 只做配置读取、依赖装配、生命周期和插件启动。
- 消息适配层负责把 OneBot/NapCat 事件转换为稳定的领域模型。
- 会话层负责上下文边界、历史裁剪、并发、超时和取消。
- 模型适配层统一模型请求、结构化输出、工具调用、Token 用量和错误转换。
- 人格与策略使用配置或明确的数据模型表达，不在消息处理器中散落字符串。
- 工具只返回可验证的结构化结果；模型不能凭空声称工具已经完成。
- 渠道层只负责把结构化回复发送到 QQ，不负责重新判断用户意图。

## 5. 数据与安全

- 使用 `httpx` 访问 HTTP 服务；领域数据优先使用 `dataclass`，持久化实体使用项目
  既有的 Tortoise 模式。
- Token、Cookie、QQ 号、用户标识、设备标识、模型请求内容和会话隐私不得写入日志、
  文档、测试快照或提交。
- 日志记录事件、状态和关联 ID，不记录完整群聊原文或完整提示词；需要排查时使用
  脱敏 fixture。
- 缓存和会话文件采用临时文件、`fsync`、`os.replace` 的原子写入策略。
- 对外部服务失败要明确区分超时、鉴权失败、限流、无结果和内部异常，禁止静默吞错。

## 6. 命令、配置与测试同步

当前 `commands.toml` 没有实际用户命令。以后新增或修改命令时，必须同步检查：

1. 处理器中的触发词、参数、权限和失败提示。
2. `commands.toml` 中唯一且大小写不敏感的 `name`、`usage`、`description` 和管理标记。
3. 本插件 `README.md` 的用户说明。
4. 若能力面向所有用户或改变根帮助内容，根 `README.md`。
5. 单元测试、对话评测 fixture 和必要的集成测试。

涉及配置变更时，还必须确认是否真的需要新增配置项，并为助手名称使用脱离具体名称的
测试值验证注入链路。

测试必须覆盖至少以下行为：

- 正常对话、无关群聊和明确唤醒的边界。
- 多轮上下文、并发消息、超时、取消和重复事件。
- 模型结构化输出失败、工具失败和外部服务局部失败。
- 敏感信息脱敏及机器人自身消息过滤。
- 人格或提示词变化对应的代表性对话回归用例。

在插件目录执行：

```bash
uv run pytest
git diff --check
```

涉及跨插件、NapCat 或模型真实请求时，再按根 `AGENTS.md` 的要求补充相邻模块测试；
网络测试必须显式开启，默认测试不能依赖第三方服务可用。

## 7. 文档与设计

- 用户可见命令和使用方式写在 `README.md`，不在本文件重复维护。
- 系统架构变化回到根 `ARCHITECTURE.md`；长期规范放在 `docs/spec/`；形成新设计时在
  `docs/feature/YYYYMMDD-slug/` 建立特性档案。
- Pumpkin 的设计与实现基线见
  [`docs/feature/20261020-pumpkin-agent/design.md`](../../docs/feature/20261020-pumpkin-agent/design.md)；
  实现推进时先更新设计，再修改代码。
- 设计文档只描述已确认的边界和当前实现，不把实验性想法写成事实。
